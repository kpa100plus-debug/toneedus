## 외부 연동이란

| 연결 대상 | 실제 서비스에서 하는 일 |
|---|---|
| 본인확인기관 | 기관이 확인한 실명·휴대전화 정보를 서버에서 검증 |
| 국세청 사업자 API | 사업자등록 정보와 휴업·폐업 여부 확인 |
| 결제대행사(PG) | 의뢰자의 카드결제·취소·환불 처리 |
| 지급대행사 | 수행자 계좌·명의 확인 및 보상금 송금 |

이메일 인증과 Google·NAVER 로그인은 위 실명확인·금전 기능과 별개다.

## 일반 회원: 실제 미션에 연결한 가상 거래

이메일 인증한 의뢰자와 수행자가 **각자 자기 계정으로** 실제 미션·TEASER·후보선정까지 진행한 뒤, 같은 미션에서 이후 거래 단계를 가상으로 시험한다. 관리자 권한이나 외부기관 키는 필요하지 않다. 가상 거래 시작과 실제 결제·지급 활성화는 서로 다른 동작이다.

### 계정과 미션 준비

1. 기존 미션의 의뢰자 계정과 TEASER를 제출한 수행자 계정을 사용하고 두 계정 모두 이메일 인증을 확인한다. 한 회원이 다른 미션에서 의뢰자·수행자 역할을 바꿔 활동하는 구조는 유지한다.
2. 서로 다른 브라우저 프로필, 일반 창과 시크릿 창, 또는 PC와 모바일을 사용한다. **같은 브라우저의 일반 탭 두 개는 로그인 쿠키를 공유하므로 분리 계정 시험에 사용하지 않는다.**
3. 의뢰자 세션에서 이미 등록된 **「도로 환경 개선 제안해주세요」·보상금 10,000,000원** 미션을 연다. 기존 미션과 접수된 TEASER 2건을 그대로 사용하며, 같은 시험을 위해 새 미션이나 중복 TEASER를 만들 필요가 없다.
4. **내 클리어 → 진행상황 → TEASER 후보 심사**에서 기존 제안 2건을 비교한다. 아직 후보가 없으면 원하는 제안의 **수행자 후보로 선택**을 누른다. 이미 선택한 후보가 있다면 그 후보로 계속한다. 이후 단계의 수행자는 반드시 해당 제안을 제출한 자기 계정으로 접속한다.
5. 현재 후보 카드에서 **이 후보로 가상 진행 시작**을 누른다. 후보선정 상태만으로 거래가 확정되거나 보상금이 확보되지는 않는다. 가상 진행 안내에 동의한 뒤 **가상 최종 수행자 확정 · 시작**을 눌러야 다음 단계로 진행한다.

사용 가능한 기존 미션·제안이 전혀 없는 경우에만 별도 테스트 미션과 TEASER를 만든다. 이 경우 제목·본문에 가상 거래 시험임을 명확히 적고 실제 모집·송금을 약속하지 않으며, 성공조건과 제출할 결과물을 구체적으로 작성한다.

### 가상 최종선정부터 지급 완료까지

아래 단계는 미션 상세의 연결 가상 거래 화면에서 진행한다. 각 계정은 자신에게 허용된 버튼만 사용한다. 한 화면에서 의뢰자와 수행자 역할을 임의로 바꾸는 방식이 아니다.

| 순서 | 실행 계정 | 시험할 동작 | 확인할 가상 상태 |
|---|---|---|---|
| 1 | 의뢰자 | **가상 최종 수행자 확정 · 시작** | 보상금 확보 대기 (`FUNDING_REQUIRED`) |
| 2 | 의뢰자 | **가상 결제 실패 체험**, **가상 결제 취소 체험** | 보상금 확보 대기 유지, 재시도 가능 |
| 3 | 의뢰자 | **가상 보상금 확보** 또는 **가상 결제 재시도 · 승인** | 가상 수행 단계 (`EXECUTING`) |
| 4 | 선정 수행자 | **가상 수행 시작** | 선정된 자기 계정만 진행 가능 |
| 5 | 선정 수행자 | **가상 수행 결과 제출** → 설명·선택 증빙 URL 입력 → **가상 결과 제출 · 의뢰자에게 검수 요청** | 가상 결과 검수 대기 (`PROOF_SUBMITTED`) |
| 6 | 의뢰자 | **보완 요청 · 재제출** → 사유 입력 → **보완 요청 · 가상 결과 재제출 받기** | 가상 수행 단계로 복귀, 재제출 가능 |
| 7 | 선정 수행자 | 보완 요청을 확인하고 **가상 수행 결과 제출**로 수정·재제출 | 다시 가상 결과 검수 대기 |
| 8 | 의뢰자 | **가상 결과 승인 · 클리어 확정** | 가상 클리어 (`SUCCESS`), 가상 지급 처리 대기 (`PROCESSING`) |
| 9 | 의뢰자 | **가상 지급 실패 체험** | 가상 지급 실패 (`FAILED`), 재시도 가능 |
| 10 | 의뢰자 | **가상 지급 재시도 · 완료** | 가상 지급 완료 (`PAID`), 실제 송금 0원 |

검수 승인은 지급 완료와 다르다. 실패 시험을 생략할 때는 **가상 보상 지급 완료**로 지급을 마친다. 수행자는 자기 세션에서 의뢰자의 검수 결과와 지급 상태를 확인하며, 의뢰자 대신 검수·지급 버튼을 실행할 수 없다. 원래 미션·TEASER 상태는 가상 진행으로 변경하지 않는다.

### 가상 진행 취소와 다시 시작

가상 지급 완료(`PAID`) 전에는 의뢰자가 가상 진행을 종료할 수 있다. 보상금 확보 전에는 **가상 진행 취소**, 확보 후에는 **가상 진행 종료 · 가상 확보금 환불**을 누른다. 확보된 가상 금액만 가상으로 환불하며 실제 청구·환불·송금은 모두 0원이다.

취소되면 이전 가상 거래의 진행 잠금이 해제된다. 현재 후보를 확인한 뒤 **현재 후보로 새 가상 진행 시작**을 눌러 새 기록으로 다시 시작한다. 이전 거래와 결제·환불·결과·이벤트 이력은 보존하며, 기존 기록을 초기화하거나 지급 완료 기록을 덮어쓰지 않는다.

### 1천만원 예시의 금액 확인

| 항목 | 금액 |
|---|---:|
| 원래 미션의 가상 보상금 | 10,000,000원 |
| 플랫폼 수수료 10% | 1,000,000원 |
| 수행자 가상 수령액 90% | 9,000,000원 |
| 실제 카드 청구·계좌이체·송금 | **0원** |

서버가 원래 미션의 보상금으로 수수료와 수령액을 계산한다. 화면이나 요청에서 보낸 임의 금액을 결제액으로 사용하지 않는다. 완료 화면과 진행 이력에도 가상 거래임과 실제 청구·송금 0원이 표시되어야 한다.

### 상태 갱신과 권한 확인

- 상대방이 단계를 진행한 뒤 자기 계정에서 **내 클리어 → 진행상황**을 연다. 상세 화면은 8초마다 갱신되며, **진행 새로고침**으로 즉시 확인할 수 있다. 같은 미션에서 이어서 진행할 수 있어야 한다.
- 페이지 새로고침·로그아웃 후 재로그인에도 가상 거래와 결과 제출·반려·재제출 이력이 유지되어야 한다.
- 같은 버튼을 중복 클릭하거나 동일 요청을 다시 보내도 가상 결제·지급과 이력이 중복 처리되면 안 된다.
- 오래 열린 화면에서 다른 세션이 이미 상태를 바꾼 경우 최신 상태를 다시 불러온 뒤 진행한다. 후보가 교체되거나 원래 미션이 취소되면 이전 후보의 가상 거래를 계속할 수 없어야 한다.
- 선정되지 않은 다른 회원은 가상 거래의 결과·증빙·진행내역을 조회하거나 변경할 수 없다. **관리자도 해당 미션의 거래 당사자가 아니면 이 회원용 가상 거래에 접근할 수 없다.**
- 회원의 실제 본인확인·사업자 인증, 실제 결과물·정산, TRUST·Strike·잔액·매출은 가상 동작으로 변경하지 않는다.

### 개발·운영 검수용 계약

회원용 연결 가상 거래는 `GET/POST /api/challenges/:id/mission-simulation`을 사용한다. 시작은 실제 의뢰자가 현재 후보의 `teaserId`, `consent:true`, `requestId`를 전달한다. 이후 동작은 `requestId`와 현재 `revision`으로 중복 처리와 오래된 상태의 갱신을 방지한다.

| 동작 | 서버 action |
|---|---|
| 가상 최종선정 | `START` |
| 가상 결제 승인·실패·취소 | `PAY_APPROVE` / `PAY_FAIL` / `PAY_CANCEL` |
| 가상 수행 시작 | `BEGIN` |
| 가상 결과 제출·재제출 | `SUBMIT_PROOF` (`description`, `evidenceUrl`) |
| 가상 결과 승인·반려 | `REVIEW_ACCEPT` / `REVIEW_REJECT` (`reason`) |
| 가상 지급 성공·실패 | `PAYOUT_SUCCESS` / `PAYOUT_FAIL` |
| 가상 진행 취소·가상 확보금 환불 | `CANCEL` (가상 지급 완료 전) |

거래 진행은 별도 `mission_simulations` 데이터와 가상 이벤트에 저장한다. 실제 결제·결과물·정산 테이블에 가상 성공 기록을 넣지 않는다. 이 경로의 성공 응답을 외부기관 본인확인, 카드 승인 또는 은행 송금 성공의 증거로 사용하지 않는다.

## 관리자: 독립된 연동 전 시뮬레이터

기존 관리자 시뮬레이터는 **관리자 한 명이 가상 의뢰자·가상 수행자 역할을 번갈아 시험하는 별도 기능**이다. 위의 실제 두 회원·미션 연결 시험과 구분한다.

1. 기존 관리자 계정으로 로그인한다.
2. 관리자 또는 내 클리어의 **연동 전 테스트** 안내에서 **10만원 예제로 바로 시작**을 누른다.
3. 의뢰자·수행자 역할을 바꾸며 가상 본인확인, 활동 주체 선택과 가상 자격 확인을 시험한다.
4. 가상 도전자 제안 접수 → 후보 선택 → 최종 수행자 선택 순서로 진행한다.
5. 결제 실패·결제창 취소·결제 승인을 차례로 눌러 재시도를 확인한다.
6. 필요하면 부분환불을 실행한다. 10만원 중 2만원을 환불하면 남은 보상금 8만원, 수수료 8천원, 가상 지급액 7만2천원이다.
7. 수행자 역할에서 결과를 제출하고 의뢰자 역할에서 검수한다.
8. 수행자의 가상 본인확인·자격·예금주 확인 후 지급 실패와 재시도를 시험한다.
9. 다시 열어도 내 테스트 기록과 진행 상태가 유지되는지 확인한다.

직접 주소: https://modu-challenge.yeit.workers.dev/#/simulation

별도 키·카드번호·계좌번호·신분증을 입력하지 않는다. 관리자 본인의 격리된 테스트 기록에만 저장하며 다른 관리자의 테스트에는 접근할 수 없다. 실제 미션을 복제해서 테스트할 때도 원본 미션은 바뀌지 않는다.

## 두 가상 테스트의 공통 확인 범위

- 가상 인증은 실제 기관 인증이 아니다. 실제 회원의 인증 배지·TRUST·Strike·잔액·매출·정산 정보를 갱신하지 않는다.
- 가상 승인·환불·지급은 실제 청구·환불·송금 **0원**이다.
- 외부 본인확인·PG·은행 네트워크에 요청하지 않는다.
- 실제 기관의 팝업·SMS·카드 승인·계좌 송금 성공은 계약과 자격증명 연결 후 별도로 시험해야 한다.
- 운영의 `moneyEnabled=false`, `moneyMode=disabled`, `PUBLIC_MONEY_ENABLED=false`를 유지한다.
